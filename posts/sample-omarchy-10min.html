这不是把几份安装命令抄到 Gentoo 上就结束了。Omarchy on Gentoo 真正要解决的，是上游配方怎样变成 ebuild、上游更新怎样持续进入 overlay、构建失败怎样被提前发现，以及用户究竟该从哪个仓库安装、又有哪些东西不归这套移植负责。这条视频就沿着这四层，把这个项目从定位、目录结构、维护闭环一直讲到实际安装。

最值得记住的判断是：这不是一次性的手工移植，而是一套由上游同步、转换规则、每夜实际构建、问题追踪和镜像发布组成的持续维护流程。对用户来说，日常只需要维护并同步 omarchy overlay；如果需要完整桌面，再补上 guru 和 hyproverlay，而不是直接修改生成出来的镜像仓库。

如果你正在 Gentoo 上尝试 Omarchy，这期能帮你分清开发仓库、用户侧 overlay 和 Portage 仓库名之间的区别，也能理解仓库优先级为什么重要、安装命令各自会拉入什么、USE 约束和许可证要怎样处理，以及内核和引导程序为什么仍然需要用户自己负责。

要点

  1. 先看项目定位。Omarchy on Gentoo 是把 Omarchy 桌面环境移植到 Gentoo Linux 的社区项目，不属于上游 Omarchy，也不提供所谓“Gentoo 官方版”。它覆盖 Hyprland、quickshell 以及周边工具，并以源码构建的 ebuild 形式提供。README 给出的安装思路，是让 Gentoo 的 Portage 管理一个额外仓库，再通过 `omarchy/omarchy` 或 `omarchy/omarchy-base` 安装桌面核心或完整默认应用集合。
  2. 这里有三个名称，最容易混淆。项目正式名称是“Omarchy on Gentoo”；GitHub 开发仓库的地址仍叫 `omarchy-gentoo`，保持小写和连字符格式；用户实际配置给 Portage 的仓库名则是 `omarchy`。这三个名字分别描述项目品牌、开发仓库位置和 Portage 仓库标识，看到不同名称时，先确认自己处于开发入口还是用户安装入口。
  3. 开发仓库 `Lax/omarchy-gentoo` 是维护工作的中心，但普通用户日常添加给 Portage 的并不是这个仓库，而是 `Lax/omarchy-overlay`。CI 会在开发仓库每次合并到 master 后，把其中的 `gentoo/` 目录重新发布到前者。用户侧 README 明确说，这个 overlay 树是生成出来的，不要直接编辑，也不要向它提交 PR；问题应反馈到 `omarchy-gentoo` 的 issue tracker。
  4. 为什么坚持区分开发仓库和发布仓库？因为开发仓库里不仅有最终 ebuild，还包含上游配方、转换工具、辅助脚本和自动化流程；发布仓库则只承担给 Portage 使用的稳定输出。把两者分开，用户能持续同步生成结果，维护者也能集中修改规则，而不必让用户手动处理大量生成文件。
  5. 仓库目录本身说明了移植是怎么拆分的。`omarchy-pkgs/` 是指向 `omacom/omarchy-pkgs` 的子模块，用来固定上游 Arch recipes；`gentoo/` 保存最终发布的 ebuild overlay；`helpers/` 放转换规则以及已移植、已跳过的记录；`bin/` 提供 `ai-port`、`sync-gentoo`、`scaffold-ebuild`、`gentoo-resolve` 等工具；`.github/` 下则有三套工作流，分别负责检查、工具自测和上游同步。
  6. 这也意味着，它不是简单把 Arch 的包名逐行替换成 Gentoo 的 atom。项目同时维护转换规则、跳过状态和工具脚本，目的就是把上游 Arch 配方稳定地翻译为 Gentoo 可管理的 ebuild。README 进一步把完整约定放在 `docs/gentoo.md`，其中包括翻译规则、范围和这套自我维护闭环；`AGENTS.md` 则是供自动化编码代理使用的 playbook。
  7. 自动跟随上游是这套项目最核心的设计。上游 Omarchy 的配方更新后，项目会同步对应的 Arch recipes，再由转换和检查流程更新 Gentoo overlay，并把结果重新发布。这样用户不需要自己逐个比对包，也不需要等维护者手工搬运每次变化；同步关系覆盖的是项目固定的 `omarchy-pkgs` 上游配方来源。
  8. 光有同步还不够，因为配方能生成，不代表一定能在 Gentoo 上成功构建。因此项目每晚会实际构建一个软件包，用真实构建尽早发现 breakage。这个机制的价值在于把问题暴露在维护流程中，而不是等到用户安装时才看到编译失败；README 描述的就是“每夜构建一个包”，没有给出固定包名或构建成功率，所以不能把它夸成每天全量测试所有内容。
  9. 构建流程还处理了需要判断的情况。如果自动流程发现某件事不能直接决定，它会自动创建一个 issue，让问题进入可见的跟踪状态；如果后续一次绿色运行通过，对应问题又会自动关闭。也就是说，自动化不只是机械搬运，还把“发现异常”和“确认恢复”串成了闭环。
  10. 发布内容还有可追踪的来源记录。每次发布都会记录生成该 overlay 所对应的 `omarchy-gentoo` master 提交，以及它所反映的 `omacom/omarchy-pkgs` 提交；用户可以在 `PROVENANCE` 和镜像提交信息中查看这些来源。这样遇到包发生变化时，至少能够从发布结果追回它对应的是哪次上游内容。
  11. 用户添加 overlay 的首选方式是使用 `eselect-repository`。先运行 `eselect repository add omarchy git https://github.com/Lax/omarchy-overlay.git`，再执行 `emaint sync -r omarchy`。前者负责添加仓库，后者从远端同步内容。README 给出的命令没有包含额外的系统安装步骤，因此这里只能说明仓库添加与同步流程，不能把整条命令理解为无需准备即可完成 Omarchy 安装。
  12. 如果系统没有 `eselect-repository`，就手动写入仓库配置。文件可放在 `/etc/portage/repos.conf/omarchy.conf`，内容包含仓库名 `omarchy`、本地位置 ``、`sync-type = git`、同步地址以及 `priority = 50`。同步地址与 `eselect` 添加时使用的 GitHub 仓库一致，区别只是改为手写配置文件。
  13. 使用 `eselect` 时还要注意一个容易漏掉的步骤：`eselect` 会写入仓库位置、同步类型和同步地址，但它不会设置优先级。需要在它写入的 `/etc/portage/repos.conf/eselect-repo.conf` 中找到 `[omarchy]` 段，再补上 `priority = 100`。README 中的手写示例使用 `priority = 50`；材料只展示了这两个具体值，并没有规定所有系统必须使用同一个数字。
  14. 为什么要处理优先级？因为 Portage 可能同时看到多个仓库提供的同名包。README 举的例子是 quickshell，它也存在于 `guru`。为了让带 `omarchy` 标签的 atom 胜出，需要让 omarchy 仓库拥有更高的仓库优先级，而不是只完成 `emaint sync`。这相当于 Gentoo 侧对“同名包选谁”作出明确选择。
  15. 桌面核心还依赖两个配套仓库，需要和 omarchy 一起启用。材料给出的命令是 `eselect repository enable guru`、`eselect repository add hyproverlay git https://codeberg.org/hyproverlay/hyproverlay.git`，然后执行 `emaint sync -r guru -r hyproverlay`。原因是 `omarchy/omarchy` 会从这两个配套 overlay 拉取 Hyprland 和 quickshell，不能只添加主 overlay 就假定所有依赖已经可用。
  16. 完成仓库准备后，最小安装是 `emerge omarchy/omarchy`。README 将它称为 desktop core，具体包括 Hyprland 会话、quickshell 桌面 shell、SDDM 登录管理器、PipeWire 音频、屏幕共享 portal，以及 Omarchy 的命令行、主题和默认设置。也就是说，这个包提供的是桌面核心组合，不等于 Gentoo 的内核、引导程序和全部启动栈。
  17. 如果想安装上游 ISO 附带的完整默认应用集合，则使用 `emerge omarchy/omarchy-base`。材料明确写的是 147 个软件包，范围包括浏览器、终端工具、打印和容器等。两者关系是：`omarchy-base` 包含桌面核心，再加上默认应用集合；但对于 Gentoo 已不再提供或仅属于 Arch 的条目，它们会被排除，具体省略项及原因列在 `omarchy-base` 的 ebuild 注释中。
  18. 这里有一条清晰的维护边界：内核和 bootloader 不属于这次移植范围，Arch 的 boot stack 也被有意排除。因此，即使桌面核心或完整应用集合安装成功，Gentoo 用户仍然要自己维护内核与引导配置。这个项目解决的是 Omarchy 桌面及周边软件如何进入 Gentoo，而不是替用户重做 Gentoo 的启动栈。
  19. 在执行 `emerge` 前还要检查三类 Portage 条件。第一，所有项目内容都使用 `~amd64` 或 `~arm64` 关键词，需要像接受其他 unstable 包一样接受这些关键词；第二，带 `-bin` 的软件包携带专有许可证，需要按常规接受相应许可，例如在 `/etc/portage/package.license` 中配置 `*/* all-rights-reserved`；第三，这些内容会在本机从源码构建，桌面规模的依赖闭包会花一些时间。
  20. USE 约束也需要准备。README 建议安装时使用 `--autounmask-write --autounmask-continue --autounmask-backtrack=y`。如果运行中报告 USE 约束冲突，例如 `dev-qt/qtbase` 的 `libproxy` 同时要求 `network`，就把隐含要求一起启用到 `/etc/portage/package.use`，然后重新运行。这里的重点不是背某个固定 flag，而是遇到冲突时补全相关约束，再继续 Portage 的解析流程。
  21. 仓库同步也不是装完一次就结束。README 要求用 `emaint sync -r omarchy` 保持 overlay 内容最新，安装核心或完整集合时还要同步 `guru` 和 `hyproverlay`。结合维护端的自动上游同步与每夜构建，用户侧的核心动作就是定期拉取新的生成结果，并依据新增的 ebuild 注释、许可、关键词和 USE 要求处理变化。

边界说明
